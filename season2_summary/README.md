# Season 2 赛季总结

本目录是 Season 2 的赛季总结产出，独立于运行代码，不影响 `werewolf_game/`
下的进化 harness 本身。包含：

- `compute_ratings.py`：统计脚本，读取全部历史评测数据，计算测试胜率、全局
  胜率、调和胜率，并拟合**两个**强度模型（Logistic 团队模型=推荐口径；
  团队 Bradley-Terry=已知退化失效，保留作对照），各自附带相对同角色 base
  节点的显著性检验（`z_vs_base` / `significant_vs_base`）。
- `compare_models.py`：对比两个模型，用"strength 是否只是胜率的线性缩放"
  作为退化判据，输出相关系数与变异系数对照表。
- `render_tree.py`：按进化树父子关系渲染每个角色的节点树，标注各项胜率、
  强度与显著性。用法：`python3 render_tree.py [role ...]`，
  `--model bradley_terry_legacy` 可切换到对照模型。
- `ALGORITHM.md`：各项指标的算法说明、公式推导、已知局限，以及实现过程中
  发现并修正的三个真实问题的完整调试记录（归一化 bug、Fisher 信息公式 bug、
  模型退化失效）。
- `output/`：统计结果，可重新运行 `compute_ratings.py` 覆盖生成。两个文件
  都采用"一个文件、内部多张表"的结构，四张表内容一致，只是格式不同：
  - `node_ratings.json`：`dataset`（数据集概况）、`node_meta`（节点元信息
    + 与模型无关的胜率指标）、`models.logistic_team` 与
    `models.bradley_terry_legacy`（两个模型各一张表，结构相同，便于横向
    对比同一节点在不同模型下的强度与显著性）。
  - `node_ratings.csv`：同样四张表，用 `# TABLE: <name>` 注释行分隔，
    每张表自带表头、表间空一行；模型表前还有 `#` 注释说明该模型的定义与
    参数（如 `team_intercept`）。用 Excel/pandas 读取时按 `# TABLE:` 切分。

重新生成全部结果：

```
cd season2_summary
python3 compute_ratings.py   # 约数十秒，生成 output/ 下两个文件
python3 compare_models.py    # 打印两模型对照（退化判据）
python3 render_tree.py       # 打印全部角色的树形展示
```

## 1. 背景：为什么要做这次统计

Season 2 的候选筛选流程只用"测试胜率"（节点作为 focus 节点被单独评测的
~20 局胜率）做保留/淘汰判断。`SEASON3.md` 已经指出这个口径至少有两个问题：

1. 只统计节点作为**焦点**出场的对局，忽略了它在其他节点评测时作为队友/
   对手出场的间接证据，样本量被人为限制在 20 局左右。
2. 没有校正队友/对手强度——跟强队友搭档虚高胜率、跟弱队友搭档虚低胜率，
   "焦点胜率"分不清"策略强"和"运气好/队友强"。

这次统计补充了三个新指标，并对 Season 2 全部 154 个节点、约 2358 局去重后
的真实历史对局重新做了评估。

## 2. 数据规模

- 6 个角色（wolf / villager / seer / witch / guard / hunter），Season 2
  累计生成 **154 个进化节点**。
- 按 `record_path` 全局去重后，共 **2358 局**唯一真实对局进入统计（详见
  `ALGORITHM.md` 第 0 节，去重是必须的，否则同一局会被重复计入）。
- 154 个节点中，**34 个从未进入真实评测**（pending，或在 smoke test 阶段
  因语法错误/超时被淘汰），没有任何对局观测，不参与胜率和强度计算。
- 各角色节点数与状态分布：

  |---|---|---|---|---|---|
  | wolf | 22 | 18 | 3 | 1 | 18 |
  | villager | 28 | 18 | 8 | 2 | 20 |
  | seer | 31 | 19 | 11 | 1 | 24 |
  | witch | 22 | 18 | 4 | 0 | 20 |
  | guard | 24 | 19 | 5 | 0 | 19 |
  | hunter | 27 | 19 | 8 | 0 | 19 |

## 3. 核心发现

### 3.1 阵营基线严重不平衡：狼人天然占优

这是本次统计里最重要、也最值得 Season 3 优先处理的发现。全部去重后对局的
获胜阵营分布：

```
狼人阵营获胜 1758 局 / 2358 局 = 74.6%
好人阵营获胜  600 局 / 2358 局 = 25.4%
```

按节点聚合看更明显：**狼人节点平均全局胜率 74.8%**（n=18），**好人阵营
全部节点平均全局胜率只有 24.3%**（n=102，覆盖 villager/seer/witch/guard/
hunter 五个角色）。也就是说，不管好人阵营内部哪个角色的候选策略进化得
再好，整体胜率天花板都被这个 3:1 的阵营基线死死压住。

这不是候选策略的问题，是 Season 2 规则配置（12 人局、4 狼 4 民 4 神职的
配比、或者信息可见性/夜晚顺序等规则细节）本身对狼人阵营友好。Season 3
在设计评测协议、进化目标时应该考虑：

- 是否需要先校准/调整基础规则配置，让阵营胜率更接近 50/50，否则"好人阵营
  策略进化得好不好"这个信号会被阵营基线噪声淹没；
  或者，
- 如果保留当前规则不变，评测和选择协议里应该按阵营分别设定筛选阈值，而不是
  用同一套全局胜率标准要求两个阵营的节点。

### 3.2 各角色 base 节点到最强候选：点估计 vs 统计显著性

用 **Logistic 团队模型**的强度估计（推荐口径，见 `ALGORITHM.md` 第 2.7
节）比较每个角色 base 节点和该角色最强候选：

| 角色 | base 强度 (胜率/局数) | 最强候选 | 最强强度 (胜率/局数) | 强度提升 | z 值 | 显著？ | base 在同角色内排名 |
|---|---|---|---|---|---|---|---|
| seer | 0.853 (24.9%/398局) | seer-n00112 | 1.758 (34.6%/26局) | +106.1% | +1.39 | 否 | 16/24 |
| witch | 0.974 (26.1%/348局) | witch-n00096 | 1.520 (29.6%/54局) | +56.0% | +0.96 | 否 | 13/20 |
| hunter | 1.177 (27.7%/376局) | hunter-n00144 | 1.585 (32.5%/40局) | +34.6% | +0.61 | 否 | 7/19 |
| guard | 1.146 (27.2%/426局) | guard-n00034 | 1.375 (30.3%/178局) | +20.0% | +0.46 | 否 | 8/19 |
| wolf | 1.028 (74.1%/328局) | wolf-n00135 | 1.162 (86.0%/43局) | +13.1% | +0.35 | 否 | 9/18 |
| villager | 1.132 (29.6%/368局) | villager-n00029 | 1.151 (31.5%/108局) | +1.7% | +0.05 | 否 | 3/20 |

注意强度值只能在**同角色内部**比较——`wolf` 的强度看起来不再远高于好人
阵营角色，是因为新模型把"狼人阵营天然占优"这部分单独抽成了阵营基线截距
`beta_0 = 1.475`（`sigmoid(1.475) ≈ 81%`），不再混进节点强度里。

**结论一：没有任何角色的最强候选相对 base 达到统计显著**（全部
`|z| < 1.5`，低于 95% 置信水平要求的 `|z| > 2`）。对全部 114 个可检验
节点逐一检验，同样无一达到 `|z| > 2`（最大 `|z| = 1.71`）。这个结论在
新旧两个模型下都成立，不是模型选型造成的假象。所以表中"强度提升 X%"
只是点估计层面的差异，统计上还不能排除"候选与 base 真实水平相同、观测
差异源于随机波动"。

**结论二：base 在新模型下的排名普遍比旧模型更靠后**，这与"base 几乎
不利用跨轮历史、应该偏弱"的实际情况吻合得更好：

| 角色 | 旧模型 base 排名 | 新模型 base 排名 |
|---|---|---|
| seer | 9/24 | **16/24** |
| witch | 6/20 | **13/20** |
| guard | 4/19 | **8/19** |
| hunter | 4/19 | **7/19** |
| wolf | 10/18 | 9/18 |
| villager | 2/20 | 3/20 |

旧模型（团队 Bradley-Terry）把 base 排得偏高，根因是它**退化成了胜率的
线性缩放**（与 `global_win_rate` 的 Pearson r = 0.985），而好人阵营各
角色的全局胜率被 3:1 的阵营基线压缩在 24%~30% 的狭窄区间里，导致节点
之间的真实差异无法体现。新模型把阵营基线抽成截距后，角色内部的策略差异
才浮现出来。完整的退化诊断与修正见 `ALGORITHM.md` 第 2.6、2.7 节，
运行 `python3 compare_models.py` 可复现对照数据。

**关于"数据够不够"**：候选节点的全局出场局数（26~178 局）本身不算少。
但好人阵营的团队强度由 5 个角色节点共同决定，单节点的边际影响被其余 4 个
稀释，这是结构性限制——局数增长只能以 `sqrt(n)` 速度改善置信区间，无法
线性抵消稀释效应。要更高效地分离单节点强度，需要改评测协议（见第 4 节
第 6 条），而不是单纯堆局数。

以下是另一个独立于统计显著性、单纯从代码实现角度确认的问题——base
节点携带的历史信息量远小于人们的预期，值得记录（但这本身是"base 应该
弱"的证据，不是"base 强度为什么不够低"的解释，两者是不同的问题，此处
仅作为背景说明）：

- 引擎的 `build_turn_packet` 本身准备了 `visible_events` 字段，包含该玩家
  从游戏开始到当前为止全部依规则可见的历史事件（发言、投票、死亡等）。
- 但 base 版本的 `task_agent.py` 组装 prompt 时**没有使用**
  `visible_events`，只用了 `public_state`（只含当前轮次/阶段/存活状态的
  瞬时快照，不含任何历史）。
- `observe()` 方法显式丢弃跨行动的公开同步（`del sync_packet`），
  `history_policy` 写的是 `"current_state_only"`。
- 唯一能碰到一点历史的途径是一个受限工具 `read_current_round_dialogue`，
  它靠 `NIGHT_STARTED`/`DAY_STARTED`/`SHERIFF_ELECTION_STARTED` 等标记事件
  定位"本轮起始序号"，把更早轮次的内容物理裁掉，只返回当前轮；且需要模型
  主动决定调用，还有调用次数预算。
- 夜间同步阶段本该传递的 `public_events` 也随 `observe()` 的
  `del sync_packet` 一起被丢弃，不是权限过滤掉，是代码主动丢弃。

也就是说 base 版本每次决策几乎是"这一刻孤立作答"，既不知道前几轮谁被
查杀、票型怎么演变，也不会主动去查。它在同角色内部排名不差，靠的完全是
底层语言模型在极度受限信息下的即时推理能力（比如从当前存活名单、当前
发言、自己的私有信息直接推断），不是靠积累的证据链。

这一点不能反过来当作"强度提升不显著"的解释——抽查过的强候选
（`wolf-n00135`/`seer-n00087`/`witch-n00097`/`guard-n00034`）在代码层面
都确实实现了结构化记忆（`_game_memory`/`_seer_memory`/`compact_memory`/
`_update_guard_memory`），只是记忆窗口普遍被压缩到最近 2~6 条摘要（受
`max_prompt_chars` 等运行时预算硬约束）。记忆机制存在且方向正确，但
"强度提升是否显著"和"是否建立了记忆机制"是两个独立的问题：前者受限于
上面 3.2 节说明的统计功效上限，不能用来反推候选是否真的没做记忆优化。

注意 `witch-n00097` 是 discarded 状态——它测试胜率 35%、全局胜率也是 35%
（只出场了 20 局，等于测试胜率和全局胜率完全重合，没有额外样本），说明
它被淘汰不是因为策略差，可能是撞上了其他筛选条件（fallback/超时等工程性
指标）。这类"策略可能不错但被工程性指标误淘汰"的节点值得人工复查。

### 3.3 测试胜率 vs 全局胜率：小样本噪声的直接证据

以下节点的测试胜率（20 局）和全局胜率（更大样本）偏差最大，直接证明了
`SEASON3.md` 提出的担忧——小样本焦点胜率不能代表真实水平：

| 节点 | 测试胜率 | 全局胜率 | 偏差 | 全局出场局数 |
|---|---|---|---|---|
| witch-n00095 | 50.0% | 26.7% | 23.3pt | 90 |
| guard-n00071 | 45.0% | 24.5% | 20.5pt | 53 |
| wolf-n00004 | 95.0% | 77.1% | 17.9pt | 354 |
| guard-base | 10.0% | 27.2% | 17.2pt | 426 |
| seer-n00123 | 10.0% | 26.7% | 16.7pt | 45 |

`guard-base` 是个典型例子：如果 Season 2 只看测试胜率（10%），这个 base
节点看起来很差；但全局胜率（基于 426 局的更大样本）显示真实水平在 27.2%，
跟其他 guard 节点差不多。20 局的测试评测样本量太小，噪声完全可以把一个
正常水平的节点的观测胜率压到远低于真实水平（或者反过来推高）。

### 3.4 调和胜率的实际表现

调和胜率（`harmonic_index_clipped`）对狼人节点整体不适用（见 `ALGORITHM.md`
第 3 节第 5 点，狼人没有异质队友概念），对好人阵营节点可以在**同角色内部**
做相对排序参考，但不建议跨角色比较，也不建议当作严格的实力估计——它本质
是一个经验加权指数，不是概率，数值本身没有绝对意义。**Logistic 团队模型的
强度估计（`models.logistic_team` 表）是本次统计推荐的主口径。**

## 4. 结论与对 Season 3 的建议

1. **阵营基线不平衡是当前最大的评测噪声源**，建议 Season 3 启动前先确认
   是否需要调整规则配置，或者在评测协议里显式区分阵营，分别设定筛选/比较
   标准，而不是用同一套全局阈值套两个胜率基线完全不同的阵营。
2. **测试胜率（20 局）噪声大**，`SEASON3.md` 提出的"开发集/选择集/密封
   保留集三段式评测"和更大样本的全局胜率是正确方向，本次统计的全局胜率
   和 Logistic 团队模型强度可以直接作为该协议的参考实现起点。
3. **调和胜率公式本身有数值稳定性问题**（不是概率、除以小分母发散、无
   样本量校正、狼人阵营不适用），建议不再作为独立指标使用，改用 Logistic
   团队模型的强度 + 标准误作为主要的"控制对手/队友强度后的真实水平"估计
   工具，详见 `ALGORITHM.md` 第 2.7、3 节。
4. **模型选型本身需要审慎验证**：本次工作中最初采用的团队 Bradley-Terry
   （强度直接相加）在 12 人局场景下退化为"胜率 × 常数"（与胜率 Pearson
   r = 0.985），完全没起到剥离队友/对手混杂的作用，根因是 12 座位强度求和
   后团队总量近似常数（变异系数 0.108），单节点变化被摊薄。改用 Logistic
   团队模型（对数尺度线性叠加 + 阵营基线截距 + L2 岭惩罚）后，与胜率的
   相关性降到 r = 0.221，base 节点排名也相应后移（更符合"base 弱"的实际
   情况）。**教训：评估一个强度模型是否有效，应当先检查它的输出是否只是
   原始胜率的单调变换**——这个判据已实现为 `compare_models.py`，Season 3
   若再换模型应沿用同样的检验。
5. **没有任何角色的最强候选相对 base 达到统计显著（`|z| < 1.5`，见 3.2
   节）**，"某些角色进化收益低于其他角色"这类基于点估计排序的说法，本质是
   在比较噪声量级本身不同的差异，不能得出"策略空间已见顶"或"候选生成有
   系统性瓶颈"的结论——目前数据不足以区分"真的没提升"和"提升了但还没被
   证明"。这个结论在新旧两个模型下都成立。
6. 部分 discarded 节点（如 `witch-n00097`）测试胜率不低，被淘汰可能是
   撞上工程性筛选条件（fallback/超时），而非策略本身差，建议人工复查这批
   "高胜率但被淘汰"的节点，避免好的策略被误杀。
7. **好人阵营 5 角色团队叠加结构稀释了单节点的可辨识信息量**（详见
   `ALGORITHM.md` 第 2.6、2.7 节），这是团队评测的统计功效上限，不是靠
   增加对局数就能线性解决的问题。Season 3 设计评测协议时，应该考虑控制
   变量的评测方式（比如固定其余队友为 base、只让待测节点变化，做更接近
   "双人对战"式的干净比较），而不是继续用当前这种"5 个角色节点自由组合"
   的团队评测去做细粒度的强度排序。
8. base 节点确实携带极少的跨轮历史信息（详见 3.2 节末尾的代码证据：
   `visible_events` 被准备好但未被使用，`observe()` 丢弃夜间同步），这
   是一个独立于统计显著性问题的、值得关注的实现现状，但**不能**用它来
   反推"候选没有利用历史"——已抽查的强候选确实实现了结构化记忆。这提示
   Season 3 如果要评估"记忆机制的真实收益"，需要单独设计对照实验（比如
   同一个候选分别在"允许用记忆"和"禁用记忆"两种设定下评测），而不是从
   胜率差异去反推。

## 5. 如何查看单个角色的完整进化树

```
python3 render_tree.py wolf                              # 只看狼人
python3 render_tree.py seer hunter                       # 多个角色
python3 render_tree.py --model bradley_terry_legacy wolf # 切到对照模型
```

树形输出中 `[✓]` = retained，`[✗]` = discarded，`[…]` = pending；每个节点
标注测试胜率/局数、全局胜率/全局出场局数、调和指数（裁剪版）、Logistic
